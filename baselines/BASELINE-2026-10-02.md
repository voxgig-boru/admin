# Boru libraries — compilation & performance baseline

**Date:** 2026-10-02
**boru:** `64c5ab2` (boru-lang/boru `main`, 2026-09-30) — one execution path:
every program is pre-flight checked, compiled to bytecode and run on the VM,
or fails `[boru/compile_failed]`. There is no interpreter fallback, and
`--compile` / `--force-compile` / `--no-compile` are retired.
**Build:** `cd cmd/go && GOWORK=off GOFLAGS=-mod=mod go build -o boru ./boru`
(CI parity; `GOFLAGS=-mod=mod` alone fails inside a checkout, which carries a
`go.work`).
**Host:** a shared 4-CPU cloud container (load 1–8 during the runs).

open migration PR:

On boru main, before these migrations, **every suite of the seven
implemented libraries was blocked**. The causes were the `aql:` → `boru:`
module prefix, `/r` → `/v`, file-relative imports, backtick escapes, and new
compile refusals; each library's dx-report "Migration" section gives its
starting state.

### Runtime callbacks — 97.7% compiled

A program compiling is not the whole story: callbacks built at run time
(function values handed to `each`, `fold`, `Tui.run`, or `boru:test`'s
property machinery) are stamped individually and, if a stamp declines, run on
the interpreter. `boru -compile-report` per suite
([`compile-report-2026-10-02.txt`](compile-report-2026-10-02.txt)):

| | count |
|---|---|
| runtime callbacks stamped (compiled to the VM) | **3,785** |
| runtime callbacks declined (run on the interpreter) | **89** |
| suites with every callback compiled (or none built) | **43 / 58** |
| suites with a declined callback | 15 — all property-test suites |
| library functions declining | **0** |

The 89 declines are all in test files' closures:

| reason | count |
|---|---:|
| `closure storedfn$body: unapplied fn-value in body residual (dynamic apply not lowered)` — a `boru:test` property generator applying its random source's `r.int` | 81 |
| `finalize left the unit unstamped` | 6 |
| `undef of the loop-carried def \`rule\` (Stage 3)` | 1 |
| `fn storedfn$body: body result of unknown provenance` | 1 |

The first reason is recorded upstream with a one-line repro (boru
`design/COMPILABLE-SUBSET.md` §5, boru-lang/boru#528). Fixing that one shape
would take the libraries to 85 / 89 of the remaining gap.

## Upstream defects found (recorded in boru-lang/boru#528)

Answer divergences (`NUR.md`, Pending), measured interpreter vs compiled:

| record | defect | silent? | hit |
|---|---|---|---|
| NUR366 | a declined stored fn breaking its return count raises `internal_error`, not `type_error` | no | — |
| NUR367 | a local rebound in a `for`/`while` body, read bare in an arm after the loop, comes back uncalled | **yes** | decision `unique` |
| NUR368 | a run-time fn value applied at the main program applies late (`print (41 f) 7` prints 41, leaves 8) | **yes** | decision (calling a returned `then`) |
| NUR369 | a re-entered fn-value param called from an `each` callback applies the inner call's fn | **yes** | template nested blocks |
| NUR370 | a fn param called on a body-local def raises `DISPATCH_GENERIC` | no | template |
| NUR371 | a callee's fold-body def clobbers the caller's same-named local | no | template |
| NUR372 | a fold body reading its param raises `undefined_word` on the 5th–8th compile in a process | no | template filters |

Compile refusals (`design/COMPILABLE-SUBSET.md` §5): a file-imported fn whose
result is a bare gradual read declines its stamp (decision); calling a
run-time fn value (most spellings); a nested var-binding `each` at top level
("twin regime", aless); the compile pass's 500,000-step analysis budget,
exhausted, misreported as a compiler defect (aless); the property-generator
callback shape above.

Recorded only in the libraries' `dx-report.md` (no compiler ledger fits):
the `boru:test` type-ID collision (`expected X, got X`; bloom-filter, stats),
`Assert.equal` passing zero values of different types as equal (decision,
trie, aless), several `boru check` false positives, and a live-TUI callback
fallback that loses locals (aless, no standalone repro).

## Performance

Whole-process wall time, best of 3, on the only path (compiled)
([`bench-2026-10-02.txt`](bench-2026-10-02.txt)). RATIO = 2026-07-29 COMPILE
column (`--force-compile`, also fully compiled, compile cost included) ÷ now;
**> 1 = faster now**. 46 suites have a July row (aless's split app suites,
`cache` and `graph` do not; aless's July app row is the pre-split suite).

| group | suites | median ratio | range | total now | total July |
|---|---:|---:|---|---:|---:|
| fixed-work unit / smoke suites | 30 | **0.14** (~7× slower) | 0.06 – 0.26 | 142 s | 15 s |
| property suites (`*_prop_*`) | 16 | 0.65 | 0.14 – 1.31 | 129 s | 73 s |
| all 58 suites | 58 | — | — | 372 s | — |

The slowdown is a **per-run fixed cost**, not slower execution:

- Property suites, whose time is the generator loop, sit near July's
  numbers (`bloom_prop_spec` 1.31, `trie_prop_spec` 1.27, `sort_prop_spec`
  1.02), except where each property also pays per-run compiles
  (`template_prop_spec` 0.18: every render compiles a sandbox program).
- Fixed-work suites pay 0.5–6 s per run regardless of how little they
  execute. Startup is 57 ms (`print 1`), and the static pre-flight check is
  6–22% of a run (decision_unit_test 263 of 1,162 ms; bloom_unit_test 100 of
  662; template_unit_test 500 of 6,145; sort_unit_test 291 of 4,673;
  stats_unit_test 394 of 2,854; trie_unit_test 278 of 2,560). The rest is
  the compile pass, which also executes the program's top level under
  check-mode analysis (aless dx-report item A), plus the VM run. It is not
  decomposed further here.
- aless's headless app suites are the extreme case (~50 s each, budget-bound
  analysis of ~100 `Aless.feed` calls).
- template renders cost ~210 ms each (~14× the interpreter era), because the
  `boru:vm` sub-engine checks and compiles every generated program
  (template `bench/BASELINE.md`).

|---|---:|---:|---:|
| bloom-filter/bloom_prop_spec | 2738 | 2086 | **1.31** |

| bloom-filter/bloom_prop_test | 1061 | 950 | **1.12** |

## Reproduce

```bash
BORU=/path/to/boru LIBS_DIR=/path/to/checkouts MD=1 bash bench/verify-libs.sh   # correctness sweep
BORU=/path/to/boru LIBS_DIR=/path/to/checkouts \
  BASELINE=baselines/bench-2026-07-29.txt bash bench/bench-libs.sh           # timings vs July
cd <lib> && boru -compile-report test/<suite>.aql                            # per-callback stamps
```

The correctness sweep here was taken with `verify-libs.sh` before its
2026-10-02 hardening (8b625f6: a missing `all green`, a missing library and a
SIGPIPE-masked marker no longer read as a pass). No row is affected: every
assertion suite printed `all green`, and no run failed.
